Linking a Sigma rule to ATT&CK in STIX 2.1 without creating duplicates

Three small decisions decide whether a STIX bundle merges cleanly into a threat intelligence platform or fills it with copies. A worked example with an indicator, an attack-pattern and the right relationship.

  • threat intelligence
  • stix
  • sigma

A Sigma rule says how to detect something. ATT&CK says what that something is. STIX 2.1 can connect the two, so a threat intelligence platform shows the detection next to the technique and the groups that use it.

It is easy to build a bundle that is valid STIX and still behaves badly once imported. These are the decisions I had to make when I added STIX output to Sigma Generator, and why.

The three objects

A minimal bundle that links one rule to one technique needs three objects:

}

Nothing here is exotic. The details are what matter.

Decision 1: pattern_type is sigma

A STIX indicator does not have to hold a STIX pattern. The pattern_type property takes values from an open vocabulary that includes stix, sigma, yara, snort, suricata and pcre. For a Sigma rule, set pattern_type to sigma and put the rule’s YAML text in pattern.

Do not translate the rule into a STIX pattern. The two languages do not describe the same things, and a translated rule is no longer the rule your SIEM runs.

Decision 2: reuse MITRE’s identifier for the technique

This is the one that causes duplicates.

Every object in MITRE’s ATT&CK STIX data has a fixed ID. LSASS Memory, T1003.001, is always attack-pattern--65f2d882-3f41-4d48-8a06-29af77ec9f90.

If your code creates a new attack-pattern with a freshly generated UUID, a platform that already has the ATT&CK dataset loaded now has two objects called “LSASS Memory”. Your indicator points at the copy. Analysts browsing the real technique never see your detection.

Look the technique up in the ATT&CK bundle and use its ID. The platform then recognises it as the object it already has and attaches your relationship to it.

The same applies to groups and software. APT28 is intrusion-set--bef4c620-0787-42a8-a96d-b7eb6e85917c in ATT&CK. Use that, not a new one.

Decision 3: the relationship is indicates

The STIX 2.1 specification defines which relationship types are expected between which objects. From an indicator to an attack-pattern, the defined relationship is indicates.

ATT&CK’s own data uses a custom detects relationship, from its data components and detection strategies to techniques. It is tempting to copy that. I chose indicates because it is the relationship the specification defines for this pair, so any STIX 2.1 consumer understands it without knowing ATT&CK’s extensions.

Smaller things that help

Give the indicator the rule’s UUID. A Sigma rule already has an id. Using the same UUID in indicator--<uuid> means one identity for the same detection in both places, and re-importing an updated rule updates the existing indicator.

Make IDs deterministic when you regenerate. Random UUIDs for relationships create new objects on every run. Deriving them with UUIDv5 from the source and target IDs makes repeated runs produce identical bundles.

Use confidence honestly. It is an integer from 0 to 100. A rule built from an exact event ID reference deserves a higher value than one inferred from a platform name. A platform can filter on it.

Label quality. A label such as quality.strong or quality.weak lets an analyst separate alert-ready detections from hunting queries without opening each one.

Mark the data. Attach a TLP marking through object_marking_refs. The STIX 2.1 specification publishes fixed marking-definition objects for TLP. Copy them exactly and do not create your own.

A quick test

After importing a bundle into a platform such as OpenCTI, check three things:

  1. Search for the technique by its ATT&CK ID. There should be one result.
  2. Open it. Your indicator should appear among its relationships.
  3. Import the same bundle again. Object counts should not change.

If the second import adds objects, an ID is being generated randomly somewhere.

Summary

Valid STIX is a low bar. A bundle is useful when it merges into what the platform already knows: the right pattern_type, MITRE’s own identifiers, and the relationship the specification defines.
