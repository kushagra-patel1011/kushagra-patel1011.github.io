Six habits for Sigma rules that hold up outside the lab

The rule-writing habits I picked up from SigmaHQ's conventions while building a Sigma rule generator, with examples of each.

  • detection engineering
  • sigma

A Sigma rule that fires on your test command is the easy part. The hard part is a rule that still works six months later, in an environment full of software you have never heard of, triaged by someone who did not write it.

I have not run detections in a production SOC. These habits come from studying SigmaHQ’s rules and conventions while building Sigma Generator, and from the mistakes my own generated rules made.

1. Detect the behaviour, not the tool

A rule that matches mimikatz.exe catches people who do not rename files. A rule that matches the behaviour catches the technique.

Compare a filename match with a rule that looks at what the process is and what it was asked to do:

detection:
  selection_image:
    - Image|endswith: '\rundll32.exe'
    - OriginalFileName: 'RUNDLL32.EXE'
  selection_dll:
    CommandLine|contains: 'comsvcs'
  selection_export:
    CommandLine|contains:
      - 'MiniDump'
      - '#24'
  condition: all of selection_*

OriginalFileName comes from the file’s version resource, so it survives a rename. The #24 variant covers callers that use the export ordinal instead of its name. Ask of every rule: what is the cheapest change an attacker could make to avoid this?

2. Name your selections and filters

Sigma lets you name detection blocks anything. Use that. A consistent convention makes conditions readable and tuning safe:

detection:
  selection_parent:
    ParentImage|endswith:
      - '\winword.exe'
      - '\excel.exe'
      - '\outlook.exe'
  selection_child:
    Image|endswith:
      - '\powershell.exe'
      - '\cmd.exe'
      - '\wscript.exe'
  filter_main_known_addin:
    CommandLine|contains: 'C:\Program Files\Contoso\Addin\'
  filter_optional_sccm:
    ParentCommandLine|contains: 'CCM\SystemTemp'
  condition: all of selection_* and not 1 of filter_main_* and not 1 of filter_optional_*

filter_main_* holds exclusions that are true everywhere. filter_optional_* holds exclusions that depend on the environment. When someone adds a filter later, the condition does not need to change, and a reviewer can see at a glance what was excluded and why.

3. Make exclusions as narrow as the evidence

The fastest way to break a rule is an exclusion like User|contains: 'svc'. It silences today’s false positive and every attacker who compromises a service account.

A good exclusion matches on more than one property of the benign activity: the parent process and the path and the command line pattern. If you cannot describe the benign case that precisely, you do not understand it well enough to exclude it yet.

4. Write for the analyst, not for yourself

The person triaging the alert at night has thirty seconds to decide what it is. Three fields do most of the work:

  • description: what the behaviour is and why it matters, in plain language.
  • falsepositives: the specific benign causes you know about. “Unknown” is rarely true and never helpful.
  • level: be honest. If everything is high, nothing is.

A custom field can carry the first thing to check:

fields:
  - CommandLine
  - ParentCommandLine
  - User
triage: >
  Check the parent process and whether the dump file was read or copied
  afterwards. Legitimate crash collection is launched by a service, not by
  an interactive shell.

5. Test both directions

Every rule needs two kinds of evidence:

  • It fires on the attack. Run the technique in a lab with production-equivalent logging, for example with Atomic Red Team, and keep the resulting events.
  • It stays quiet on normal activity. Run the converted query over 30 days of production data before enabling the alert.

Keep both sets as test data. When an analyst reports a false positive, add that event to the benign set. Rules get noisier far more often than they go blind, and this is how you notice.

6. Check the log source before you blame the rule

A surprising number of “broken” rules are correct logic pointed at data that is not there. Before shipping, confirm:

  • The event is actually collected. Process creation without command-line logging is common.
  • The field names match after conversion. Image in Sigma becomes a different column in each backend.
  • The fields are populated. OriginalFileName needs Sysmon or an EDR; native event 4688 does not carry it.

A quick count of events per day for the log source, with the fields you rely on, saves hours of debugging.

A short checklist

Before a rule merges, each of these should be a yes:

  1. Does it describe a behaviour an attacker cannot trivially change?
  2. Is every exclusion tied to a specific, understood benign case?
  3. Would a new analyst know what to do with the alert?
  4. Is there a test that proves it fires, and one that proves it stays quiet?
  5. Has it run against real data for long enough to trust the volume?

None of this is complicated. It is the difference between a detection library people rely on and one they learn to ignore.
