Detection Engineering · Part of Sigma Generator: Sigma rules drafted from MITRE ATT&CK

Correlation rules for attack chains and thresholds

Single-event rules miss attacks that are only suspicious as a sequence or a volume. I extended Sigma Generator to build Sigma correlation rules from ATT&CK's multi-step analytics, producing 232 of them with no repeated evidence between steps.

Try it in the browser Source on GitHub
  • 232 correlation rules across 186 techniques
  • 88% to 0% attack chains whose steps repeated the same values
  • 0 of 3,302 SigmaHQ community rules that are correlation rules

Problem

A lot of attacker behaviour is not suspicious one event at a time.

  • Credential dumping is a process opening LSASS, then a dump command, then a file or registry change. Each event has benign explanations. The sequence within a few minutes on one host does not.
  • Password spraying is not one failed logon. It is many ordinary failures from one source against many accounts.

Sigma has a specification for this: correlation rules, which combine base rules over a time window. When I checked SigmaHQ’s community release r2026-07-01, it contained 3,302 rules and no correlation rules at all. ATT&CK’s analytics, on the other hand, frequently describe multi-step behaviour and volume in plain language. That gap was the opportunity.

Approach

  1. Find ATT&CK analytics that describe more than one log source for the same behaviour, and build a temporal chain from them.
  2. Find analytics that describe volume, and build event_count or value_count rules.
  3. Take the time window and threshold from ATT&CK’s own text wherever it states one.
  4. Make each step carry independent evidence, and drop steps that do not.
  5. Validate every correlation file with pySigma, which resolves the references between rules.

Technical details

An attack chain

ATT&CK analytic AN1030 describes LSASS credential dumping across several log sources. The generator writes one multi-document file: the correlation rule first, then a named base rule per step.

title: Potential LSASS Memory Attack Chain Via 3 Correlated Log Sources
status: experimental
tags:
    - attack.credential-access
    - attack.t1003
    - attack.t1003.001
correlation:
    type: temporal
    rules:
        - step1_process_access
        - step2_process_creation
        - step3_registry_set
    group-by:
        - Computer
    timespan: 5m
level: critical
---
name: step1_process_access
logsource:
    category: process_access
    product: windows
detection:
    selection_target:
        TargetImage|endswith:
            - '\lsass.exe'
    selection_indicator_source:
        SourceImage|endswith:
            - '\mimikatz.exe'
            - '\procdump.exe'
            - '\rundll32.exe'
            - '\werfault.exe'
    selection_indicator_access:
        GrantedAccess:
            - '0x1f0fff'
    condition: selection_target and 1 of selection_indicator_*
---
name: step2_process_creation
logsource:
    category: process_creation
    product: windows
detection:
    selection_indicator_content:
        CommandLine|contains:
            - comsvcs.dll
            - Invoke-Mimikatz
    condition: selection_indicator_content

The five-minute window is not my guess. It comes from ATT&CK’s tuning note for that analytic, which gives the time between LSASS access and dump file creation as an example of five minutes.

The bug that made chains meaningless

My first implementation had a serious flaw that I only found by measuring: in 88% of chains, the steps repeated the same values. If step one matches lsass.exe in a process-access event and step two matches lsass.exe as command-line text, the “chain” is the same evidence counted twice. It looks like correlation and adds nothing.

The fix was a set of rules for how evidence is assigned:

  • Values are claimed once. lsass.exe belongs to the process-access step, so it is not reused in the next one. Subject values (the registry key, the accessed process, the file) go to the step whose telemetry actually records them.
  • A step must be behavioural. A step left with only its event type or only generic values is dropped.
  • Fewer than two steps left means no chain. In the example above, a fourth dump-file step was dropped because its only values were a Windows DLL path, which the attack uses but does not write, and a generic folder.

After this change, chains with a value repeated between steps went from 88% to zero.

Counting rules

Where ATT&CK describes volume, the generator writes a threshold over a base event:

correlation:
    type: value_count
    rules:
        - base_security            # EventID 4625, 4771, 4648
    group-by:
        - IpAddress
    timespan: 10m
    condition:
        field: TargetUserName
        gte: 5

That is password spraying: five or more distinct target accounts failing from one address inside ten minutes. Wording such as “different accounts” or “unique destination IPs” produces value_count, which counts distinct values. Otherwise matching events are counted with event_count.

Teaching it what “volume” means

The first version over-triggered here too. The word “volume” appears in ATT&CK for reasons that have nothing to do with counting:

  • Disk paths such as /Volumes/ on macOS.
  • Phrases like “frequently abused”.
  • Byte-rate tuning knobs such as OutboundDataRateThreshold.
  • Amounts described as benign, for example “allowlist of high-volume domains”.

Volume now has to mean an amount of countable activity: “a high volume of failed logons”, “number of unique destinations”. Thresholds come from ATT&CK’s text when it states one, such as “more than 20 failed logons”. Otherwise a default of 10 events or 5 distinct values is used, and the file’s banner says the number is a default.

Other decisions

  • Grouping is by host on Windows, or by account for cloud logs. A host-scoped step is never correlated with an account-scoped one.
  • Windows longer than 24 hours in ATT&CK’s text are treated as thresholds, not time windows.
  • The level is raised one step above the single-event rule, as the specification intends.
  • Ordering. The type is temporal. Where ATT&CK’s wording implies order (“subsequently”, “followed by”), the banner suggests switching to temporal_ordered once confirmed.

Results

  • 232 correlation rules across 186 techniques: 110 attack chains, 112 event_count rules and 10 value_count rules.
  • 0 chains with a value repeated between steps, down from 88%.
  • 0 pySigma failures. Every chain’s rule references resolve.
  • Across the 176 ATT&CK threat-group packs, the generator produces 1,892 correlation rules alongside 4,036 single-event rules.

Lessons

  • Measure the thing you assume is fine. I only found the repeated-evidence problem because I counted it. The chains looked reasonable when I read a few by hand.
  • Borrow the numbers. Taking time windows and thresholds from ATT&CK’s own tuning notes makes each rule defensible, and the banner cites the sentence it came from.
  • Know the limits. A temporal chain needs every step to fire. Where ATT&CK says a dump or a registry change follows, an analyst has to remove the steps their environment will not see. Not every SIEM backend can convert Sigma correlations yet either. Both are documented in the tool.
