Threat Intelligence

IOC validation and STIX 2.1 automation at Seqrite Labs

As a Threat Research Intern I built a pipeline that checks indicators against VirusTotal, AbuseIPDB, OTX and ThreatFox, automated STIX 2.1 bundle creation for OpenCTI, and modelled an APT28 tracking profile.

  • 4 intelligence sources checked per indicator
  • 1 threat actor, APT28, modelled end to end in OpenCTI

Problem

Indicators of compromise arrive faster than an analyst can assess them. Before an IP address, domain or file hash is used in a detection or passed to a SOC, someone has to answer basic questions: is it still malicious, who else has seen it, and what is it associated with?

During my internship that assessment was manual. Each indicator meant opening several services, searching for the same value in each one, and comparing the answers by hand. The work is repetitive, it is easy to skip a source when the queue is long, and two people can reach different conclusions about the same indicator.

This page describes the design of what I built. It does not include indicators, data or tooling details from Seqrite.

Approach

  1. Query several independent sources for every indicator instead of trusting one.
  2. Normalise the answers into one record per indicator.
  3. Represent the result as STIX 2.1, so it can be loaded into a threat intelligence platform.
  4. Model a threat actor end to end in OpenCTI to test that the structure supports campaign-level analysis.
  5. Map indicators to ATT&CK techniques and Sigma rules, so intelligence connects to detection.

Technical details

Why four sources

Each service answers a different question, which is why the pipeline uses all four:

Source What it contributes What it cannot tell you
VirusTotal Verdicts from many antivirus engines and scanners for files, URLs, domains and IPs Who is behind it, or whether it is still in use
AbuseIPDB Community abuse reports for IP addresses, with a confidence score from 0 to 100 Anything about domains or files
AlienVault OTX Community “pulses” that tie an indicator to a reported campaign or malware How reliable the person who published the pulse is
ThreatFox Indicators shared through abuse.ch, linked to a named malware family Indicators nobody has submitted yet

No single column is enough. A file hash with many VirusTotal detections is strong evidence on its own. An IP address with one old abuse report is not, because the same address may now belong to someone else. Putting the four answers side by side is what turns a lookup into an assessment.

One record per indicator

The four APIs return different shapes of JSON, different names for the same idea, and scores on different scales. The pipeline’s job is to turn them into one record per indicator that an analyst can read in seconds: the indicator, its type, what each source said, and when each source last saw it.

Three practical problems shape a pipeline like this:

  • Not every source covers every type. AbuseIPDB only knows IP addresses, so “no result” for a domain means “not applicable”, not “clean”. The record has to keep those two answers apart.
  • Free API tiers are rate limited. VirusTotal’s public API, for example, allows four lookups a minute. Requests have to be queued and spaced, and repeat lookups for the same indicator should be answered from a cache.
  • Indicators age. An address that hosted a command-and-control server last year may be an ordinary website today. The date of the last sighting matters as much as the verdict.

STIX 2.1 bundles

A spreadsheet of indicators cannot say how they relate to each other. STIX 2.1 can: every indicator, malware family and threat group is an object with its own ID, and relationship objects connect them. I automated the creation of these bundles for APT scenario modelling, so the output could be loaded into OpenCTI rather than retyped.

The example below shows the idea. It uses a reserved documentation domain, not an indicator from the internship. The intrusion set ID is the real, public MITRE ATT&CK identifier for APT28.

{
  "type": "bundle",
  "id": "bundle--5d0092c5-5f74-4287-9642-33f4c354e56d",
  "objects": [
    {
      "type": "indicator",
      "spec_version": "2.1",
      "id": "indicator--8e2e2d2b-17d4-4cbf-938f-98ee46b3cd3f",
      "created": "2026-05-12T09:00:00.000Z",
      "modified": "2026-05-12T09:00:00.000Z",
      "name": "Credential phishing domain",
      "pattern": "[domain-name:value = 'login.example.com']",
      "pattern_type": "stix",
      "valid_from": "2026-05-12T09:00:00.000Z"
    },
    {
      "type": "relationship",
      "spec_version": "2.1",
      "id": "relationship--44298a74-ba52-4f0c-87a3-1824e67d7fad",
      "created": "2026-05-12T09:00:00.000Z",
      "modified": "2026-05-12T09:00:00.000Z",
      "relationship_type": "indicates",
      "source_ref": "indicator--8e2e2d2b-17d4-4cbf-938f-98ee46b3cd3f",
      "target_ref": "intrusion-set--bef4c620-0787-42a8-a96d-b7eb6e85917c"
    }
  ]
}

The relationship object is the valuable part. It is what lets a platform answer “show me everything connected to this group” instead of “search for this string”.

APT28 tracking profile in OpenCTI

To check that the structure held up for a real actor, I modelled an APT28 tracking profile in OpenCTI. APT28 (ATT&CK group G0007, also reported as Fancy Bear and Forest Blizzard) is one of the most thoroughly documented groups in public reporting, which makes it a good test case.

OpenCTI treats each kind of indicator as its own observable type: IP addresses, domain names, URLs, file hashes, email addresses and so on. The profile linked these indicator types to the one intrusion set, so that an analyst starting from any single indicator could move outward to the campaign it belonged to and document the case in one place.

Linking intelligence to detection

An indicator on its own says “this value is bad”. It does not say what the attacker was doing. The link to MITRE ATT&CK comes from context: what the reporting says the indicator was used for.

Indicator and its context ATT&CK technique Where a rule would look
Domain used in a phishing link T1566.002 Spearphishing Link Email gateway and proxy logs
IP address used for command and control over HTTPS T1071.001 Web Protocols Proxy and firewall logs
Hash of a malicious attachment T1566.001 Spearphishing Attachment Endpoint file and process events

I mapped indicators to technique IDs in this way and aligned them with Sigma detection rules, so that a piece of intelligence pointed at the log source and rule that could act on it. I wrote more about the STIX side of that link in Linking Sigma rules to ATT&CK in STIX 2.1.

Results

  • Indicator assessment that had been done by hand across four services was automated, which reduced the time an analyst spent on each indicator.
  • Validated intelligence fed SOC detection workflows.
  • STIX 2.1 bundles were produced for ingestion into OpenCTI and downstream SIEM alert enrichment.
  • An APT28 tracking profile linked indicator types to one intrusion set for campaign-level correlation and case documentation.

Lessons

  • Disagreement between sources is information. When one service flags an indicator and three do not, the useful question is why: a new indicator, a false report, or an address that has changed hands.
  • Structure is what makes intelligence reusable. The same indicators are worth far more as linked STIX objects than as a list, because the relationships carry the meaning.
  • Indicators expire, behaviour lasts. An attacker can change a domain in minutes but changes technique far less often. Mapping indicators to ATT&CK techniques made that clear to me, and it is the idea behind my later project, Sigma Generator, which starts from the technique instead of the indicator.
