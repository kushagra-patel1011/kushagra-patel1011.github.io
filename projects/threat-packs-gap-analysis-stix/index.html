Threat Intelligence · Part of Sigma Generator: Sigma rules drafted from MITRE ATT&CK

Threat group detection packs and SigmaHQ gap analysis

Threat intelligence is only useful to a SOC when it becomes something to detect. I built the part of Sigma Generator that takes a threat group, drafts a detection for each of its techniques, shows what community rules already cover, and packages the result as a STIX 2.1 bundle.

Try it in the browser Source on GitHub
  • 176 ATT&CK threat groups with a one-command detection pack
  • 4,036 rules across all group packs, plus 1,892 correlation rules
  • 1 of 7 ATT&CK-recommended log sources SigmaHQ watches for MFA fatigue

Problem

A threat report says a group is targeting your sector. ATT&CK lists the sixty-odd techniques attributed to that group. The question a SOC lead actually asks is narrower: which of those can we already detect, and what should we build first?

Answering it by hand means opening each technique, checking the community rule set for coverage, and writing drafts for the gaps. I had done a smaller version of this during my threat research internship, mapping indicators to ATT&CK techniques and Sigma rules, and I wanted a tool that did the whole loop.

Approach

  1. Resolve the actor. Accept a group, a piece of software or a campaign, by ATT&CK ID, name or alias.
  2. Mine the actor’s own procedures first. ATT&CK’s procedure examples are its most concrete text.
  3. Check community coverage for every technique, per log source.
  4. Draft rules, optionally only for the gaps.
  5. Package everything as STIX 2.1 so a threat intelligence platform can ingest it alongside its ATT&CK feed.

Technical details

One command per actor

python -m src.main generate --group APT29 --chains
Detection pack for APT29 (G0016): 66 technique(s) attributed by ATT&CK
  58 Sigma rule(s), 26 correlation rule(s) for 58 technique(s)
  Quality: 14 strong, 39 moderate, 31 weak
  SigmaHQ r2026-07-01: no existing rule for 13 of these techniques
  2 technique(s) skipped: ATT&CK gives no concrete values
  Folder: output/packs/g0016_apt29

Aliases resolve as well, so "Cozy Bear" finds APT29. For each technique the pack prefers values from that group’s documented procedures, for example the sentence describing the group’s use of encoded PowerShell, over the technique’s generic description. Rules carry the Sigma group or software tag, such as attack.g0016.

Software packs are restricted to the platforms the software runs on. ATT&CK lists Mimikatz as Windows-only, so its pack never receives a Linux rule, even where a Linux analytic would score higher.

Gap analysis against SigmaHQ

The tool downloads SigmaHQ’s release and indexes rule metadata locally: ID, logsource, ATT&CK tags and event IDs. It then compares what ATT&CK recommends monitoring with what a community rule already watches.

python -m src.main gaps T1621
T1621 Multi-Factor Authentication Request Generation
  SigmaHQ rules tagged T1621: 2
  ATT&CK-recommended telemetry covered: 1/7  -> partial
    azure:signinlogs        -> azure/signinlogs    covered by 2 rule(s)
    NSM:Connections         -> zeek/conn           GAP
    AWS:CloudTrail          -> aws/cloudtrail      GAP
    WinEventLog:Security    -> windows/security    GAP
    auditd:AUTH             -> linux/auditd        GAP
    saas:okta               -> okta/okta           GAP
    macos:unifiedlog        -> macos/unifiedlog    GAP

MFA fatigue is a good illustration. The community rules for it only watch Azure sign-in logs, while ATT&CK recommends seven kinds of telemetry. An organisation using Okta has no community coverage for this technique at all.

How coverage is decided, so the result is not over-claimed:

  • A rule covers a log source when it is tagged with the technique and watches the same Sigma logsource.
  • For Windows service logs, the event IDs must overlap.
  • “Covered” means a rule exists for that technique on that telemetry. It does not mean the rule catches every variant, and the tool says so.

--gaps-only then generates rules only for uncovered telemetry, so the output complements the community set instead of duplicating it.

STIX 2.1 design decisions

Each pack includes a bundle. Most of the thought went into making it behave well inside a threat intelligence platform.

Object Decision Why
indicator pattern_type: sigma, with the rule as the pattern. Its UUID equals the Sigma rule’s UUID One identity for the same detection in both worlds
attack-pattern Keeps MITRE’s own STIX ID The platform deduplicates it against its existing ATT&CK feed instead of creating a second copy
relationship indicator --indicates--> attack-pattern This is the relationship the STIX 2.1 specification defines for that pair. I chose it over MITRE’s custom detects for compatibility
intrusion-set, tool, malware, campaign The actor, with MITRE’s uses relationships and procedure descriptions The pack is browsable from the actor down
report One object referencing everything in the pack A single item to open in the platform
labels Each indicator carries its quality tier, such as quality.strong An analyst can filter to deployable detections inside the platform

The indicator’s confidence is taken from the evidence tier that produced the rule, so a rule built from an exact event ID reference is marked more confident than one inferred from a platform name.

What a pack contains

output/packs/s0002_mimikatz/
├── README.md                     quality split, then technique, rules, correlations, SigmaHQ status
├── pack.json                     the same, machine-readable
├── s0002_mimikatz_bundle.json    STIX 2.1 bundle
└── sigma/                        one rule per technique, mr_*.yml are correlation rules

Results

  • Detection packs for all 176 ATT&CK threat groups: 4,036 rules and 1,892 correlation rules in total.
  • Every one of the 5,928 group-pack files passes validation and pySigma.
  • Across software packs, 102 of 10,311 rules fall outside the software’s platforms because no analytic exists for that platform. Each of those is flagged in its banner.
  • The gap check turns “do we cover this group” into a per-log-source table that can be sorted into a backlog.

Lessons

  • Intelligence needs a destination. A group profile is reading material. A list of thirteen techniques with no existing rule is work someone can pick up.
  • Reuse identifiers. Keeping MITRE’s STIX IDs and matching the Sigma UUID is a small decision that avoids duplicate objects in every platform that ingests the bundle.
  • Define “covered” narrowly and say so. It would have been easy to report better coverage numbers with a looser definition. A gap report is only useful if people trust it.
  • Attribution data is a starting point. ATT&CK records what has been publicly reported about a group. A pack is a reviewable backlog for an analyst, not a statement about what the group will do next.
