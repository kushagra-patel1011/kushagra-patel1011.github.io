Hardening a local web UI against CSRF and DNS rebinding

A localhost tool that can write files is a target for any website the user visits. I threat-modelled Sigma Generator's web UI, locked it down with only the Python standard library, and then removed the server entirely by compiling the tool to run in the browser.

Try it in the browser Source on GitHub
  • 52 to 19 MB ATT&CK data trimmed for the browser, with byte-identical output
  • 0 servers behind the browser build; rules are generated on the visitor's machine
  • 3 static files the local server will serve; no path is taken from the URL

Problem

Sigma Generator started as a command-line tool. I added a local web UI so an analyst could search ATT&CK, preview rules and save them from a browser.

That UI runs on 127.0.0.1 and can write files to disk. People tend to assume localhost services are safe because they are not exposed to the network. They are still reachable from the user’s own browser, and so is every website open in another tab. A malicious page can try to send requests to http://127.0.0.1:8765 and make the tool act on the user’s behalf.

A security tool that introduces a vulnerability on the analyst’s machine is worse than no tool. So I treated the UI as an attack surface from the start.

Approach

  1. Threat-model the local server. Who can reach it, and what can it do?
  2. Close each path with a specific control, using only the standard library so there is no dependency to audit.
  3. Test the controls, not only the features.
  4. Remove the server where possible. Build a version that runs entirely in the browser, so most users never start a local service at all.

Technical details

The threats

Threat How it works against a localhost tool
Cross-site request forgery A page on another site submits a form or request to 127.0.0.1, triggering a file write
DNS rebinding An attacker’s domain re-resolves to 127.0.0.1, so their script becomes “same-origin” with the local server
Cross-site scripting ATT&CK text or rule content rendered as HTML executes script in the UI’s origin
Path traversal A crafted URL makes the static file handler read outside its folder
Resource exhaustion Oversized or stalled requests tie up the single local process

The controls

  • Binds to 127.0.0.1 by default, and prints a warning if the user binds elsewhere.
  • Host header check. Requests whose Host is not the server itself are rejected. This is what defeats DNS rebinding: the attacker’s page sends its own hostname.
  • CSRF protection without tokens. POST requests need Content-Type: application/json plus a custom X-Requested-With header. A cross-site HTML form cannot send either, and a cross-site script cannot add the custom header without a CORS preflight the server never approves.
  • Strict Content-Security-Policy with no inline scripts, plus X-Content-Type-Options: nosniff and frame-ancestors 'none'.
  • No HTML injection. The page inserts ATT&CK and rule text with textContent, never innerHTML.
  • Static file allow-list. The server serves exactly three known files. No part of a file path comes from the URL.
  • Input limits. Request bodies are capped at 64 KB, every field is type-checked, and stalled clients time out after 60 seconds.
  • No external requests. The UI loads nothing from the Internet, so it works offline and leaks nothing.

Each of these has tests: the suite covers CSRF, the Host header, content type, body size and the static-file allow-list, alongside the feature tests.

A bug the tests found

On Windows, rejecting an oversized request sometimes reset the connection before the client had finished sending, which the browser reported as a network error instead of a clean rejection. The fix was to drain the request body before responding. Small, but it is the kind of thing that only shows up when you test the failure paths.

Removing the server

The strongest control is not running a server at all. The public demo runs the same Python code inside the browser, compiled to WebAssembly with Pyodide.

How the build works:

  1. A build script trims the ATT&CK bundle from 52 MB to 19 MB (about 3 MB compressed) by keeping only what the generator reads. A --check mode proves the generator’s output is byte-identical with the trimmed data.
  2. The project is packaged as a wheel and loaded by Pyodide in the page.
  3. A small runtime answers the page’s own /api/... requests from Python in the browser, so the user interface code is the same one the local server uses.
  4. GitHub Actions builds and deploys it to GitHub Pages.

The result: no backend, no install, and nothing the user types is sent anywhere, because there is nowhere to send it.

Two problems cost me time and are worth recording:

  • Silent data loss when trimming. ATT&CK stores data-component names in separate objects. Dropping them did not cause an error. It quietly changed which telemetry the rules used. The byte-identical check exists because of this.
  • A missed page event. The UI script starts on DOMContentLoaded. When the runtime injects that script after Pyodide has loaded, the event has already fired, so nothing started. The runtime now re-dispatches it.

Results

  • The local UI ships with protections against CSRF, DNS rebinding, XSS and path traversal, built on the standard library alone.
  • The browser build has no server and sends no user input anywhere.
  • ATT&CK data for the browser went from 52 MB to 19 MB with provably identical output.
  • Both front ends, and the CLI, share one service layer, so the security-relevant logic exists once.

Lessons

  • Localhost is not a trust boundary. The browser is the bridge between the open web and anything listening on the loopback address.
  • Custom headers are a cheap CSRF defence for an API that only its own page should call. No session or token storage is needed.
  • Prove an optimisation changed nothing. Trimming data felt safe and was not. The check that compares outputs byte for byte is what makes the smaller bundle trustworthy.
  • Removing attack surface beats defending it. Most people who try the tool now never run the local server.
