Detection Engineering

Sigma Generator: Sigma rules drafted from MITRE ATT&CK

An open-source tool I built that reads ATT&CK's detection analytics and drafts a Sigma rule for 556 techniques, grades every rule for quality, and refuses to write one when there is nothing concrete to match.

Try it in the browser Source on GitHub
  • 556 of 697 active ATT&CK techniques get a drafted rule
  • 325 techniques with a strong or moderate rule (46.6%)
  • 0 generated files failing pySigma validation

The browser version of the tool. Everything runs on the visitor’s machine.

Problem

MITRE ATT&CK tells a defender what to look for. Turning that into a working detection is manual work: read the technique, find the right log source, work out which field holds the evidence, and write the rule. For one technique that is an afternoon. For a threat group with sixty techniques it is weeks.

Tools that automate this usually have the opposite problem. They write a rule for everything, and most of those rules are noise. My own first version did exactly that: it produced 622 rules, and when I audited them, 165 (27%) were nothing more than a keyword search of ATT&CK’s prose. A rule that matches words from a description detects nothing.

The goal became narrower and more honest: draft the rules that ATT&CK’s data can actually support, say how good each one is, and write nothing where there is nothing to write.

Approach

Since version 18, ATT&CK publishes detection strategies and analytics: for each technique, the concrete log sources MITRE recommends, often down to the event ID. I built the generator on that data instead of the older free-text data sources.

The pipeline for one technique:

  1. Resolve the telemetry. Map what ATT&CK names to a Sigma logsource, and record how confident that mapping is.
  2. Pick the best log source. Rank candidates by confidence, by ATT&CK’s own ordering, and by how much of the mined content the source can express.
  3. Place values where the telemetry records them. The same string belongs in different fields in different events.
  4. Grade the result by what the detection block really contains.
  5. Refuse rather than bluff when ATT&CK gives no concrete value.

The whole pipeline is rule-based and deterministic. No machine learning model is involved, and every decision is written into the output so a reviewer can check it.

Technical details

Four tiers of evidence

The tier used becomes the rule’s stated confidence, and is carried into the STIX indicator as well.

Evidence ATT&CK gave Example Confidence
Log source and event ID Sysmon EventCode=13 to registry_set 0.95
Log source only AWS:CloudTrail to product: aws / service: cloudtrail 0.75
Data component only Module Load to image_load 0.55
Platform only IaaS to CloudTrail 0.25

Across all analytics, 98.5% of log-source references (4,098 of 4,160) resolve to a Sigma logsource.

Putting values in the right field

This is where most of the work went. A few of the rules the generator follows:

  • lsass.exe is a TargetImage in a process-access event, but command-line text in a process-creation event (procdump -ma lsass.exe).
  • Run-key rules do not require reg.exe, because most malware writes registry keys through the API.
  • Windows tools never land in Linux rules, and the reverse.
  • Registry hive prefixes are dropped, since Sysmon records HKU\<SID>\....
  • ATT&CK’s placeholder names such as example.dll are ignored.

When no platform is requested, the best-supported one wins. ATT&CK lists platforms alphabetically, so simply taking the first would favour ESXi over Windows.

Quality grading

Every rule is graded by its content:

Tier What the rule has What the generator does
strong two or more selections with specific values level follows the ATT&CK tactic
moderate one subject selection (a registry key, an accessed process, a file, a port) or several specific values level lowered one step
weak only the event type, one value, or values common in normal activity tagged detection.threat-hunting, level capped at low
no values nothing concrete in ATT&CK no rule is written

Generic alternatives are pruned too. In a list like [/etc/passwd, /bin/bash] each value matches on its own, so /bin/bash is removed and the rule’s banner says why.

Every file explains itself

Each generated rule starts with a comment banner stating the ATT&CK analytic it came from, the telemetry and its confidence, the quality tier and the reason for it, what was left out on purpose, and a checklist to work through before deploying. Every rule ships as status: experimental.

python -m src.main generate T1003.001 --chains
python -m src.main quality --group APT29 --details

Testing

  • Unit tests run offline against a slice of ATT&CK v19.2 and 168 real SigmaHQ index entries, in CI on Python 3.9 and 3.13.
  • A corpus snapshot pins the entire output. Every technique’s rule is reduced to a digest of tier, level, logsource, fields, values and condition, and committed. Any change in generated content shows up technique by technique in review.
  • Every generated file is validated with pySigma.

Results

Measured against ATT&CK Enterprise v19.2:
Techniques that get a rule 556 of 697 active
Skipped because ATT&CK names no concrete value 66
Unmappable because the telemetry lives outside a defender’s logs 75
Quality split 130 strong, 195 moderate, 231 weak
Rules backed by an exact ATT&CK event reference 445 of 556
Files failing validation or pySigma 0

What the quality work changed, compared with my first version:

First version Now
Rules written 622 556
Rules that were only a keyword search 165 (27%) 0
Broad rules marked as hunting queries none all 231 weak rules

Lessons

  • Fewer rules was the improvement. Going from 622 to 556 made the tool more useful, because every remaining rule matches on something real.
  • Grade your own output. Saying “42% of these are hunting queries, not alerts” is more credible than claiming everything is production-ready.
  • Tiers measure content, not accuracy. “Strong” means two independent signals were found in ATT&CK. It does not mean the rule was tested against an attack. Every draft still needs validation on real telemetry, and the tool says so.
  • Snapshot the whole output. Unit tests pin one behaviour at a time. The corpus snapshot is what catches a small change quietly altering two hundred rules.
  • What I would do next: behavioural testing, replaying real attack telemetry through the rules. I wrote the protocol for it but have not run it yet.
